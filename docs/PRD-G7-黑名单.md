**原始需求（用户原话）**

> 我需要能够有黑名单管理哪些应用不会被本软件识别。

**用户已拍板的 5 项决策（本 PRD 不再讨论，直接执行）**

1. **排期**：作为 G7 → **v1.8.0**，排在 G3~G6 之后。
2. **匹配依据**：**按进程名**（如 `CloudMusic.exe`、`QQMusic.exe`）。不做 AUMID 匹配、不做窗口标题匹配。
   > 注意区分：AUMID **只**在「枚举时反查真实进程名」这一步作为中间键出现（方案 B），**不参与命中判定**。
3. **拉黑语义**：**完全忽略**——被拉黑应用提供的媒体会话一律不当作媒体源：不显示信息/封面/进度、不查歌词、不响应播控；若当前只有它一个会话，小组件回落到「无媒体」空态。
4. **管理入口**：三处都做——(a) 设置页「黑名单」分区（含自动检测列表 + 手动输入 + 移除）；(b) 托盘右键「拉黑当前应用」；(c) 清单管理（增删、去重、大小写不敏感）。
5. **手输进程名的生效范围 = 方案 B**（2026-11-03 新增）：枚举时反查真实进程名并写入 **`config.json` 的 `media.app_names`（持久化，重启仍有效）**；判定侧只读「缓存 → 静态表 → AUMID 末段」三级，**运行时零新增跨进程调用**。手输分三档（保证 / 保证 / 不保证），不保证的那档**添加时就给温和提示**。详见 P0-01 / P0-04 / §6 / §7。

## 1. 背景与问题

| 现状 | 问题 |
| --- | --- |
| 小组件按 SMTC「当前会话」自动跟随，`GetCurrentSession()` 拿到谁就显示谁 | 用户无法排除特定应用。开着游戏、视频播放器、网页音乐时，任务栏可能被非音乐内容占据 |
| 「电影和电视」、浏览器（Edge 播 B 站）、某些常驻 UWP 应用都会注册 SMTC 会话 | 这些会话一旦被 Windows 判为 current，小组件就整套切过去：换封面、换歌词、播控指错对象 |
| 现有设置页 6 个分区（外观/歌词/音量/快捷键/通用/关于）没有任何「媒体源」维度的控制 | 用户唯一的手段是关掉播放器，代价过大 |

**核心诉求**：把「哪些应用算媒体源」的决定权交还用户，且这件事的成本必须**低于**「手动关掉播放器」。

## 2. 产品目标与非目标

### 2.1 产品目标（3 个，正交）

1. **可排除**：任意一个会走 SMTC 的应用，用户能让曲栏彻底无视它——不是隐藏 UI 上的某些元素，而是**从媒体源里摘掉**。
   > **v1.8.0 只有 SMTC 一条链路需要过滤。** 项目里**不存在**「WASAPI 兜底媒体链路」：`src/media/wasapi.rs` 全文只有音量枚举（系统主音量 + 会话音量），`PlaybackState::Fallback` 与 `AppEvent::FallbackSession` 均无生产点。主 PRD P1-08 描述的兜底条是历史设计残留。
2. **零后台成本**：黑名单的判定是**纯本地内存比对**（无跨进程调用）；应用探测**只在设置页按需执行**，绝不新增任何后台轮询。这一条是硬约束，不是优化项。
3. **一次设置长期有效**：写入 `config.json`，重启、换数据目录、换播放器都不丢；三处入口（设置页列表 / 手动输入 / 托盘快捷项）操作同一份数据，彼此一致。

### 2.2 非目标（明确不做）

- ❌ **WASAPI 兜底链路的过滤**——该链路不存在（见 §2.1 目标 1），不为其做任何设计与验收。
- ❌ AUMID / 包名匹配、窗口标题匹配、路径匹配、通配符 / 正则匹配。
- ❌ 「只屏蔽封面」「只屏蔽歌词」这类分级屏蔽——语义只有一种：**完全忽略**。
- ❌ 黑名单的反向模式（只允许列表内应用，白名单模式）→ P2。
- ❌ 多会话并存时自动改选「下一个未拉黑会话」→ 本期不做，回落空态（见 §7、§9）。
- ❌ 后台定时探测应用列表、托盘常驻「已忽略 N 个」气泡、拉黑时弹确认框。
- ❌ 按应用做音量 / 播控 / 歌词的独立配置。

## 4. 需求池

> 优先级沿用主 PRD 口径：**P0 = 必须实现**；**P1 = 应该实现（本期交付）**；**P2 = 可选增强（本期不实现）**。

### 4.1 P0 — 必须实现（6 条）

#### P0-01 黑名单配置字段与归一化

新增配置分组 `media`，字段 `media.blacklist`（字符串数组）。所有写入路径（设置页添加、托盘拉黑）**必须**经过同一套归一化，不接受任何绕过。

**归一化规则（产品口径，逐条给结论）**

| 输入 | 处理结果 | 说明 |
| --- | --- | --- |
| `CloudMusic.exe` | `cloudmusic.exe` | 统一小写存储 |
| `cloudmusic` | `cloudmusic.exe` | **自动补全扩展名**（用户不该被 `.exe` 卡住） |
| `CLOUDMUSIC.EXE` | `cloudmusic.exe` | 大小写不敏感（Windows 进程名本身不敏感） |
| `"C:\Program Files\NetEase\CloudMusic\CloudMusic.exe"` | `cloudmusic.exe` | **只取文件名**，路径与引号被丢弃 |
| `  QQMusic.EXE  ` | `qqmusic.exe` | 前后空白 trim |
| `.exe` / 空串 / 全空白 | **拒绝**，toast「请输入进程名」 | 文件名部分为空 |
| `*` `?.exe` `a|b.exe` `a<b.exe` | **拒绝**，toast「进程名不支持通配符或路径之外的特殊字符」 | 不做模式匹配；**非法字符是最先判定的一条**（早于补 `.exe`），否则 `a*b.exe` 会被当成合法文件名存进去 |

- **去重**：大小写不敏感（存小写后比较），重复添加返回「已在黑名单中」且配置不变。
- **顺序**：按首次添加顺序保留，**不排序**（用户看到的顺序稳定，不会自己跳）。
- **上限**：单条 ≤ 260 字符；列表 ≤ 200 条；超限拒绝并 toast。防手改 json 写坏配置。
- **手改 json 也安全**：`Config::load` 后对 `blacklist` 再归一化一次（剔空 / 剔非法 / 剔超长 / 小写 / 去重 / 截断到 200），坏值静默丢弃，不 panic、不报错弹窗。

**手输进程名的生效范围（用户 2026-11-03 拍板 = 方案 B：枚举时真实反查 + **持久化**缓存）**

背景：曲栏原本只有一张 **22 条**静态「AUMID → 进程名」对照表（`src/media/player_map.rs`），表外应用拿不到真实进程名。方案 B 补上这一环：

| 环节 | 口径 |
| --- | --- |
| 反查 | 设置页枚举时，对**静态表未命中**的会话做一次真实反查（音频会话枚举 + 逐进程查镜像名），拿到真实进程名。**静态表已命中的不反查**（值已是真实名）→ 典型机器反查 0 次 |
| 判定 | 主循环判定只读三级：「`media.app_names` 缓存 → 静态表 → AUMID 末段」，**纯内存，运行时零新增跨进程调用**（`progress.md` §2.2 第 11 条不可破） |
| 缓存存哪 | **落盘到 `config.json` 的 `media.app_names`**，类型 `BTreeMap<String,String>`（**不用 HashMap**：否则每次保存字节序都变，破坏单行 json 可 diff 的约定）。键 = AUMID 小写（trim + 小写 + 剔控制字符，≤260；`!` `_` 中文原样保留，**只用于查表不参与用户输入**）；值 = 真实进程名，**走与手输完全同一个归一化函数**。**重启后仍有效**——这是"曾经出现过就永久生效"承诺的前提 |
| 缓存上限 | **64 条**；满时淘汰 `BTreeMap` **字典序最小的键**（确定性 + 自愈：被淘汰的条目下次出现会重新学到；不存时间戳，零额外状态）。**不需要"清缓存"按钮**；「清空黑名单」**不动**缓存 |
| 负缓存 | **不做**。一次偶发失败（反查失败 / 超预算）不许被永久记住——失败只体现为这一次的 `resolved=false`，下次枚举重新尝试 |
| 缓存作用面 | 只决定「这个名字是否真实」；即使缓存全失效，静态表 + AUMID 末段仍能让功能工作，最坏后果只是某些行显示"未能验证" |

由此得到**手输生效范围 = 三档**：

| 档 | 场景 | 是否保证命中 |
| --- | --- | --- |
| **保证** | 值来自缓存或静态表（即「检测到的应用」里显示的那个名字） | ✅ 一定命中 |
| **保证** | 从「检测到的应用」点「加入」（与判定同源） | ✅ 一定命中 |
| **不保证** | 手输一个**从未在本机出现过**、又不在静态表里的进程名 | ⚠️ 只有该应用 AUMID 末段恰好等于它才命中；**添加时立刻给温和提示**，不静默 |

**不静默原则（本需求的唯一落点）**

第三档不是"悄悄加进去然后不生效"，而是**添加成功的同时**给一条温和提示（信息级 toast，**不阻断、不回滚**——用户可能在提前配置）：

> **`toast.blacklist.unverified`**
> 中：`已加入。这个进程名还没在这台机器上出现过；如果之后没生效，请到「检测到的应用」里点「加入」。`
> 英：`Added. This process name hasn't been seen on this machine yet — if it doesn't take effect, use Add in "Detected apps" instead.`

- 反之，输入 `cloudmusic.exe`（静态表命中）**不出现**这条提示——提示本身即"已验证/未验证"的信号，不能滥发。
- 该词条已在 ARCH §8.2 落位（键名与数量以该表为准，本文不另立数字）；桥接层用「已识别 / 未识别」两档承载，不用布尔。

**验收点**
- 表中 7 种输入，落盘后 `config.json` 里出现的值全部符合左列右列对照。
- 重复添加 2 次 `CloudMusic` 与 `cloudmusic.exe`，列表长度恒为 1。
- 手动往 `config.json` 塞 `["  CloudMusic  ", "", "CloudMusic.EXE", "a*b.exe"]`，重启后列表为 `["cloudmusic.exe"]`（`a*b.exe` 按 ARCH「非法字符一律拒绝」被剔除）。
- 输入 `a*b.exe` → toast 提示非法、配置不变；输入 `zzz-test.exe`（表外、缓存无）→ 条目入库 + 温和提示；输入 `cloudmusic.exe` → **无**该提示。

#### P0-02 媒体会话过滤（完全忽略语义）

**只有 SMTC 一条链路需要过滤**——项目里不存在 WASAPI 兜底媒体链路（`src/media/wasapi.rs` 全文只有音量枚举；`PlaybackState::Fallback` 与 `AppEvent::FallbackSession` 均无生产点），因此本需求**不为兜底做任何设计与验收**。

**必须在三点拦截（不是一处）**。只在「发布前」拦是不够的：播控命令执行时会**重新取一次当前会话**，只在发布点拦挡不住热键/按钮把 `PlayPause` 打到被拉黑的应用上。

| # | 拦截点 | 产品要求 |
| --- | --- | --- |
| ① | 读到会话身份之后 | 命中即**跳过**后续元数据 / 封面 / controls 的读取（省掉最贵的跨进程调用）→ 日志 60s 统计行里该应用的属性读取计数应显著下降 |
| ② | 发布 `NowPlaying` 给渲染层之前 | 命中即视为「该会话不存在」：不发事件、不更新 `TrackId`、不触发歌词、不更新进度、不请求封面。若它是唯一会话 → 会话态回落 `NoSession`（主 PRD §5.2 门控 3，小组件隐藏） |
| ③ | 播控命令执行处 | 命中即**整条丢弃**（热键 / 小组件三键 / 滚轮音量 / 托盘命令一律覆盖）。**这是必做项，不是优化** |

**忽略态的运行节奏**：进入忽略态后身份重查有 1s 下限（不得每 60ms 读一次 AUMID，否则比正常态更费），不到点整轮不做跨进程调用。这是"全拉黑也不耗电"的保证，也是解绑后 1s 内能自动恢复的原因。

**保留但不使用的能力（重要，别一起删）**

- 仍然知道「当前会话是谁」（AUMID / 进程名）。用途只有两个：托盘菜单给「恢复当前应用（应用名）」、设置页显示「已加入黑名单（N）」。**不得**因此恢复任何渲染、歌词、播控行为。
- 判定是**纯内存字符串比对**（缓存 → 静态表 → AUMID 末段三级回落）。**禁止**为此新增任何跨进程调用、禁止为此新增定时器。

**UI 表现（用户问的：是否需要提示"已忽略 N 个应用"）**

| 位置 | 表现 | 结论 |
| --- | --- | --- |
| 小组件 | 直接消失（`NoSession`），**不显示任何"已忽略"字样** | 默认静默。小组件是任务栏的一部分，多一行说明会破坏"融入任务栏"的观感 |
| 托盘 | 不弹气泡、不弹通知 | 拉黑的即时反馈就是「小组件消失了」本身，气泡属于重复提示 |
| 设置页 | 黑名单卡片标题带计数：`已加入黑名单（2）`（0 条时只显示「黑名单」） | 唯一可见的"已忽略 N 个"信息位，够了 |
| 日志 | 首次命中/变更时一条 `INFO`：`黑名单命中，忽略会话：cloudmusic.exe（网易云音乐）` | 有且仅有这一条，且**同进程名 60s 内不重复打印**（按进程名分桶，不能用按段名限流的 `RateLimiter`），否则全拉黑场景会刷爆日志 |

**验收点**
- 拉黑网易云并播放网易云：小组件不出现；日志有 1 条 `黑名单命中`；**无**该会话的 `歌词查询` / `歌词内存命中` 行；**无**封面解码行。
- 拉黑后从播控三键、滚轮、快捷键任一入口操作，均不产生任何对网易云的 SMTC 控制调用（日志无对应 `smtc.controls`）。
- 解绑黑名单后 ≤1s（忽略态身份重查下限 1000ms）恢复正常显示，无需重启。

#### P0-03 设置页「黑名单」分区（手动管理）

设置页左侧导航新增第 4 项 **「黑名单」/ `Blacklist`**（位置：音量之后、快捷键之前），内含两张卡片。

- **卡片 A「黑名单」**：列表 + 手动输入框 + 「添加」按钮 + 「清空黑名单」（P1-01）。每行显示进程名，右侧「移除」。
  - 空态文案：「黑名单为空，所有应用都会被识别为媒体源。」
  - 输入框 placeholder：「输入进程名，如 CloudMusic.exe」
  - 静态提示（第一行）：「只按进程名匹配，大小写不敏感；可不带 `.exe`；填完整路径只取文件名。**从「检测到的应用」里加入最稳。**」（末句是本版新增，因为手输是唯一不保证生效的入口）
  - 静态提示（第二行）：「提示：浏览器的进程名通常是 `msedge.exe`、`chrome.exe`，不是 `edge.exe`。」
  - **列表行要区分「已验证 / 未能验证」**：行的进程名后缀一个小标记——命中静态表或缓存的行不显示任何标记；未命中的行（用户手输的陌生名字）显示一枚淡色小字「未能验证」。鼠标悬停给出完整解释：`blacklist.detected.unverified`（见 P0-06）。
- **卡片 B「检测到的应用」**：见 P0-04。
- 添加/移除**走同一条归一化入口**（`media.blacklist_add` / `media.blacklist_remove` / 清空用 `media.blacklist_clear`，见 §6），**改完即时生效，不需要重启、不需要点保存**。
- **所有 toast 文案由 Rust 侧发出**，词条放 `src/i18n.rs`（`toast.blacklist.*`），**不要**写进 HTML 的 `I18N` 字典——HTML 字典只管静态标签与 placeholder。前端**不做**任何输入校验（校验只在归一化一处，两套规则必然漂移）。

**验收点**
- 添加后 500ms 内出现在列表，且写入 `config.json`；重启程序后仍在。
- 移除后立刻从列表消失；若它正在播放，≤1s 内小组件出现该应用的信息。
- 加入一个表外且缓存无的名字 → 该行带「未能验证」小字，且**仍然可以移除**（标记不是错误态，不阻断操作）。
- 所有 `.btn` / `input[type=text]` / `.list` 样式沿用既有 CSS 类，不新增视觉体系、**不新增 CSS 类**（外观与「本地歌词目录」卡片保持一致；灰态/淡字用既有 `.dimmed` / `.desc`）。

#### P0-04 设置页「检测到的应用」按需枚举（硬约束）

**这是本需求唯一的性能红线，写成硬约束**：本项目对 SMTC 跨进程调用有严格预算（`progress.md` §2.2 第 11 条：跨进程调用当预算管，全量轮询会把网易云拖卡）。因此：

| 约束 | 内容 |
| --- | --- |
| **允许枚举的时机** | ① 用户**首次进入**「黑名单」分区；② 用户点「刷新」按钮。**仅此两处** |
| **禁止** | 打开设置页（`ready`）就枚举 / 定时器 / `setInterval` / 后台线程轮询 / **每次切导航都枚举** / 小组件侧枚举。**一个都不许有**。理由：默认分区是「外观」，`ready` 时枚举 90% 是白花；来回点「外观 ↔ 黑名单」若每次都枚举，等于把跨进程调用变成手动轮询 |
| **执行线程** | 枚举必须跑在媒体线程（`Manager` 是 MTA 对象）；**UI 线程零参与**，不得在 WebView 回调里调 SMTC |
| **单次枚举的读取清单** | 会话列表 → 每个会话的 `SourceAppUserModelId` → **仅对静态表未命中的会话做真实进程名反查**（方案 B）→ 显示名。**到此为止**：禁止读媒体元数据（标题/歌手）、禁止读时间线、禁止读播控信息、禁止解码封面 |
| **耗时上限** | 产品可接受上限：**进入分区 / 点刷新 → 列表渲染完成 ≤300ms**（用户无感、不出现"空白等一下"）。技术硬闸由架构定：单次反查 120ms / 单次枚举总计 200ms / 最多反查 16 次 / 最多扫 64 会话，超闸的条目**降级为"未能验证"而不是失败**。UI 永不冻结（枚举在媒体线程），不得出现按钮永久置灰 |
| **失败降级** | 枚举失败（COM 异常 / manager 失效 / 超时）→ 下发**空快照**（不是"不发"），卡片显示「未检测到正在播放的应用」，不影响卡片 A 的手动输入与其他功能，日志记一条 `WARN` |
| **防连点** | 枚举期间「刷新」按钮置灰，收到快照后恢复；首次进入分区的自动枚举只触发一次（`detectedLoaded` 守卫），用户主动点刷新才重新枚举 |

**方案 B：枚举时反查真实进程名并**持久化**缓存（用户 2026-11-03 拍板）**

| 项 | 口径 |
| --- | --- |
| 为什么需要 | 曲栏只有 22 条静态 AUMID→进程名对照表，表外应用原本拿不到真实进程名 |
| 做法 | 枚举时对**静态表未命中**的会话做真实反查（音频会话枚举 + 逐进程查镜像名），拿到真实进程名；**静态表已命中的不反查** |
| 写回 | 反查结果写入 `config.json` 的 `media.app_names`（键 = 小写 AUMID，值 = 归一化后的进程名）。**重启后仍有效** |
| 主循环 | 判定只读「`media.app_names` 缓存 → 静态表 → AUMID 末段」，**运行时零新增跨进程调用** |
| 缓存上限 | **64 条**；满时淘汰字典序最小的键（自愈，不需要"清缓存"按钮；「清空黑名单」不动缓存） |
| 代价 | 只发生在用户看设置页时；典型机器反查 0 次（静态表已覆盖），最坏 = 表外会话数。**绝不允许**把它放进主循环 |
| 双闸（架构 D11） | 单次反查预算 120ms、单次枚举总预算 200ms、单次枚举最多反查 16 次、最多扫 64 个会话——**超预算的条目降级为"未能验证"而不是失败**。四个数只在 `defaults::limits` 定义，PRD 不重复定值 |

**列表显示规则**

| 项 | 规则 |
| --- | --- |
| 一行内容 | 主文本 = 应用显示名（`player_map` 已知映射，如「网易云音乐」）；未知时显示「未知应用」。副文本 = 进程名（等宽字体，如 `cloudmusic.exe`） |
| 右侧按钮 | 「加入」，点击即加入黑名单 |
| 已拉黑的应用 | **不在这张列表里显示**（加入后立即从检测列表消失、出现在黑名单列表，形成闭环反馈；两个列表显示同一项会让用户困惑）。实现上由**前端按当前配置过滤**，**不重新枚举**（重新枚举 = 多一次跨进程调用） |
| **名字未能验证**（`resolved=false`，反查失败、退到 AUMID 末段） | **仍然可加入、按钮不置灰**——因为列表里显示的**就是判定会用的值**，加入后一定命中。只在该行加一行淡色小字：`blacklist.detected.unverified` =「进程名未能验证（可能不是真实文件名，但加入后仍会按此匹配）」/ 英 `Name unverified (may differ from the real file name; matching still uses this value)` |
| 身份完全为空（连 AUMID 都没有） | 该行灰态、按钮置灰，副文本「无法解析进程名」，悬停提示「请在黑名单里手动输入进程名」。**这是唯一不可加入的行**——请与上一行区分：`resolved=false` 可点，身份为空不可点 |
| 空态 | 「未检测到正在播放的应用。」+ 小字：「只能列出正在播放或最近有媒体会话的应用；当前没在播的应用请在上方手动输入进程名。」（输入框就在紧邻的卡片 A 里） |
| 时间提示 | 卡片标题右侧小字：从未检测过显示**「尚未检测」**；检测过显示**「上次检测：HH:MM」**（时间由后端下发的时间戳在页面侧格式化）；右侧「刷新」按钮 |

**验收点**
- **进入**「黑名单」分区 → 列表出现当前在播应用（进程名 + 显示名）；**只打开设置页（停在外观分区）不产生任何枚举**。
- 点「加入」→ 该行立即消失、出现在卡片 A；小组件 ≤ 1s 内回落空态。
- 表外应用的行显示真实名（不是 AUMID 末段）+ **无**"未能验证"小字；`config.json` 的 `media.app_names` 出现新条目。
- 反查失败/超预算的行 → 有「未能验证」小字，但「加入」按钮**仍可点**且加入后真的生效。
- 点「刷新」→ 重新枚举一次（「上次检测」时间更新）；枚举期间按钮置灰。
- 在「外观 ↔ 黑名单」之间来回切 5 次 → 只发生 1 次枚举（`detectedLoaded` 守卫生效）。
- **关闭设置页后静置 5 分钟**：日志中无任何枚举记录，60s 统计行 `smtc 轮询统计` 的调用量与 v1.7.1 基线一致（±10%），无新增 `[perf]` 慢记录。

#### P0-05 托盘「拉黑当前应用 / 恢复当前应用」

托盘右键菜单新增一项，**位置：`显示/隐藏小组件` 之后、分隔线之前**。同一条菜单项按状态互斥显示：

| 当前会话状态 | 菜单项 | 可点性 |
| --- | --- | --- |
| 有会话、未拉黑 | `拉黑当前应用（网易云音乐）` | 可点 |
| 有会话、已拉黑（=「被忽略的当前会话」存在） | `恢复当前应用（网易云音乐）` | **可点**（哪怕小组件此刻因被忽略而不显示） |
| 无会话 / 会话身份解析失败 | `拉黑当前应用` | **置灰不可点**（`MF_GRAYED`；现有 `tray.rs::append` 是四参，需扩展为五参加 `enabled`——仅供参考，由架构决定实现形态） |

- **恢复入口是误拉黑的主要防线**：只要存在「被忽略的当前会话」，该项**必须**保持可点，不许写成"必须有可见会话才可点"，否则用户拉黑唯一播放器后就只剩改 json 一条路。
- **要不要二次确认？→ 不要。** 理由：拉黑是"从托盘一键消掉干扰"的场景，确认框会把这个动作变成两步；撤销成本已被压到同一菜单的第二项。
- **立即生效**：点击后立刻写配置 → 重算当前媒体 → 小组件 ≤ 1s 内消失；菜单下次打开即显示「恢复当前应用」。
- **恢复**：点击后立刻从黑名单移除该进程名 → ≤1s 内重新识别并显示（走忽略态身份重查节奏，不额外强制刷新）。
- **幂等**：同一应用连续拉黑/恢复，结果只取决于当前状态，不得累积重复项。

**验收点**
- 无会话时打开托盘菜单，该项灰显且点击无任何反应。
- 有会话时点击「拉黑当前应用」，小组件 1s 内消失；再开菜单看到「恢复当前应用（网易云音乐）」且**可点**，点击后 1s 内恢复显示。
- 连续拉黑/恢复同一应用 3 次，`config.json` 中无重复项、无残留。

## 6. 数据与持久化口径

| 项 | 口径 | 理由 / 注意 |
| --- | --- | --- |
| 文件 | `config.json`（既有单文件、单行 JSON） | 不新增独立文件，避免第二份配置源 |
| 路径 | 恒在 `platform::data_dir()` 默认根 | 项目规矩：`config.json`/`.tmp` 永远留默认根；用户改 `storage.data_dir` **不影响**黑名单位置 |
| 字段 | `media: { blacklist: Vec<String>, app_names: BTreeMap<String,String> }`，整组 `#[serde(default)]` | 缺字段 = 空数组/空表，天然向后兼容；`storage` 是"后加独立分组"的先例。**`app_names` 必须用 `BTreeMap` 而不是 `HashMap`**：否则每次保存字节序都变，破坏单行 json 可 diff 的约定 |
| 元素格式 | 黑名单：小写、纯文件名、含 `.exe`：`"cloudmusic.exe"`（不含路径、引号、通配符） | — |
| 顺序 | 黑名单：首次添加顺序，不排序 | 列表观感稳定 |
| 去重 | 大小写不敏感（等价于存小写后比较） | — |
| 上限 | 黑名单：单条 ≤260 字符、列表 ≤200 条。`app_names`：**64 条**，满时淘汰**字典序最小的键** | 防手改 json 写坏配置拖慢启动；缓存是"热点表"不是用户资产，淘汰策略确定性 + 自愈，**不需要"清缓存"按钮** |
| `app_names` 的键值 | 键 = AUMID（trim + 小写 + 剔控制字符，≤260；`!`/`_`/`.`/中文都原样保留，**只用于查表**，不参与用户输入）；值 = **与手输同一个归一化函数**的输出（小写、纯文件名、含 `.exe`） | 同源是正确性基石：列表显示的名字 = 判定用的名字 = 用户能手输命中的名字 |
| **判定的比较方式** | 比较时**只比主干**（去 `.exe`），`msedge` 与 `msedge.exe` 等价；**禁止子串匹配**——判定必须是**等值**比较，不是包含比较 | ⚠️ 防一个真实 bug：既有 `player_map::resolve()` 用的是 `contains`（子串）匹配，若黑名单照抄 `contains`，用户拉黑 `music` 会误伤 `cloudmusic.exe` / `qqmusic.exe` / `music.ui.exe`。主干比较还是"缓存没学过 / 反查失败"时的兜底判据（身份退到 AUMID 末段后，末段与该 exe 名主干相同就仍命中），但它**不是落盘的替代品**——落盘解决"重启后"，主干比较解决"从未枚举过" |
| `app_names` 的写入时机 | 只在**用户看设置页枚举**时写入（反查成功才有值）；`blacklist_clear` **不动**它 | 清空黑名单是"清用户意图"，缓存是"这台机器的客观事实"，两者无关 |
| **不做负缓存** | 反查失败 / 超预算**不写任何"查不到"标记**，只体现为这一次 `resolved=false`，下次枚举重新尝试 | 一次偶发失败不许被永久记住（安全软件临时挂钩、播放器刚启动都可能失败一次） |
| `Config.version` | **1 → 2** | 一个 `media` 分组一次引入两个字段，仍只需 1→2（版本号表达 schema 代数，不是字段计数）。⚠️ 回滚到 v1.7.1 并写过配置 → 老版本 serde 会**同时丢掉** `blacklist` 与 `app_names`，写进 release note |
| 写入链路 | 设置页/托盘 → 内存配置 → 既有 `ConfigChanged` → **同步写盘**（`cfg.save()`）→ 既有 `.tmp` + 原子替换 | **复用，不新建写盘路径**；写入是**同步、即时**的，比 500ms 更严 |
| ⚠️ 写盘口径（上一版写错） | **本项目没有 300ms 去抖**。`event.rs` 里那句「保存配置（带 300ms 去抖）」是**失实注释**（`progress.md` §2.3 第 22 条已登记，归 G6 修） | **不要承诺"去抖"，也不要顺手实现去抖**——那是 G6 的范围，本期不碰。G6 若真加了去抖，判定侧是内存立即生效，行为不受影响 |
| 读取链路 | `Config::load` → 归一化（黑名单：剔空/剔非法/剔超长/小写/去重/截断 200；`app_names`：坏键坏值逐条剔除 + 超 64 淘汰）→ 有变化即落盘 | 手改 json 也安全，永不 panic、永不弹窗 |
| 设置页桥接 | 三条路径：`media.blacklist_add`（string）、`media.blacklist_remove`（string）、`media.blacklist_clear`（bool，P1-01 用）；**不做**整数组覆写路径。写入走**唯一收口**，且要能把"这个名字已验证 / 未能验证"两档回传给页面（`bool` 表达不了），通用 `set` 路径对这三条**显式拒绝**，防止旧页面/注入脚本绕过归一化 | 沿用 `lyrics.local_dirs_add/remove` 的先例；白名单 `match`，不用反射 |
| Rust → JS | 新增消息 `{ type: "mediaApps", payload: { apps: [{ process, displayName, playable, resolved }], at } }`；`at` = epoch **毫秒**整数（页面侧格式化为 `HH:MM`，后端不写时间格式化代码）；`resolved=false` 表示"名字是猜的、但仍可加入" | 下发枚举快照；页面不持有任何轮询。**已拉黑条目照常下发，由前端按配置过滤**（后端过滤会导致"加入后行消失"必须重新枚举）。这条消息**不能**复用"配置快照"的推送通道，否则会把配置快照顶掉、重开窗口补推错内容 |
| i18n 词条 | 设置页静态标签走 HTML 内 `I18N` 字典；托盘菜单**与全部 toast** 走 `src/i18n.rs`。**键名与数量一律以 ARCH §8.1 / §8.2 表格逐条为准，本文不另立数字** | 两处都要；toast 写进 HTML 字典永远发不出去 |
| 体积影响 | 黑名单 ≤200 条 + `app_names` ≤64 条 × ~60B ≈ 4KB，总量仍 <10KB | 与主 PRD ≤8MB 包体预算无关，不引入新依赖 |

## 7. 边界与已知限制

| 场景 | 结论 |
| --- | --- |
| **当前没在播的应用** | 「检测到的应用」**列不出来**（SMTC 只暴露有会话的应用）。要拉黑只能**手动输入进程名**。这是本需求最主要的已知限制，必须写进设置页小字（§5.1 空态文案）与本文档 |
| **手输对「从没出现过的应用」不保证生效（方案 B 的残留限制，唯一一档）** | 判定只能读「`app_names` 缓存 → 静态表 → AUMID 末段」。若某应用的 AUMID 与真实进程名不一致、且它**从没进过**「检测到的应用」，用户手输的真实进程名**不保证命中**（只有 AUMID 末段恰好等于它才命中）。缓解：① 让它播一次 → 进列表 → 一键加入（必生效，且真实名会**落盘**，此后永久有效）；② 手输未命中时**立刻给温和提示**，绝不假装成功；③ 提示里直接指路「到「检测到的应用」里点加入」。**不做**判定时反查（撞 §2.2 第 11 条预算红线） |
| **`app_names` 缓存的固有代价** | ① 播放器大版本升级可能换 AUMID → 旧条目失效、新 AUMID 需重新学到（自愈：该应用下次开播 + 下次枚举即可）；② 满 64 条时淘汰字典序最小的键，理论上可能淘汰掉仍需要的条目（同样自愈，只影响"名字是否真实"，不影响黑名单是否生效）；③ **不提供"清缓存"按钮**，用户无需关心 |
| **拉黑浏览器（Edge 播 B 站）** | 会同时屏蔽该浏览器内**所有**网页媒体（YouTube / Spotify Web / B 站 / 播客）。这是设计后果，不是缺陷；设置页用静态小字提示，**不加确认框** |
| **系统自带播放器（电影和电视 / `Video.UI.exe`）** | 与第三方应用同等对待，可拉黑。它是本需求最高频的真实用例之一，需在验收时实测 |
| **多会话并存** | 只对 Windows 判定的「当前会话」做判定。当前会话被拉黑 → 回落空态，**不自动改选**其它未拉黑会话（改选需 `GetSessions` 枚举，与 §2.2 预算冲突）。已由架构裁决确认（D1） |
| **全部应用都被拉黑** | 小组件永久不出现（这才是正确语义）。要求：不崩溃、CPU ≈ 0、日志不刷屏（黑名单命中日志 60s 内同进程名限流） |
| **拉黑 `barline.exe` 自己** | 接受但永不命中（曲栏自身不产生 SMTC 会话），无害；日志无异常 |
| **被拉黑应用退出后黑名单项仍在** | 正确行为（用户意图是"永远不认它"），不自动清理。「清空黑名单」是唯一批量退出口（P1-01） |
| **WASAPI 兜底** | **不存在这条链路**，无需考虑（见 §2.1 目标 1 / P0-02） |
| **应用改名 / 换进程名** | 老条目失效、新进程名需重新拉黑（按进程名匹配的固有代价，不做 AUMID 匹配） |
| **同时开着多个会话** | 会话数越多，枚举这一次越慢（静态表外的会话才反查）；受"120ms 单次 / 200ms 总量 / 16 次 / 64 会话"四道闸保护，超闸的条目降级为"未能验证"。仍只在用户看设置页时发生，**不得**因此改成后台定时刷新 |

## 8. 验收标准（真人可验证 10 条）

> 编号说明：原第 6 条「WASAPI 兜底链路也被过滤」**已作废**（该链路不存在），原 1~5、7~8 顺延为 1~7；第 8~10 条是方案 B 的**三条专有走查**（W1/W2/W3），必须单独跑，不要混在别的条目里。

1. **拉黑生效**：拉黑 `CloudMusic.exe` 后播放网易云 → 小组件**完全不出现**（不显示信息/封面/进度/歌词）；日志有且仅有 1 条 `黑名单命中，忽略会话：cloudmusic.exe`；整个播放期间**无**该会话的 `歌词查询` / `歌词内存命中` / `封面已解码` / `smtc.controls` 行；60s 轮询统计行里该应用的属性读取计数应明显下降。
2. **撤销生效**：从托盘「恢复当前应用（网易云音乐）」撤回 → ≤1s 内小组件恢复显示网易云信息与歌词，播控三键可用。
3. **归一化**：设置页依次输入 `CloudMusic`、`CLOUDMUSIC.EXE`、`"C:\Program Files\NetEase\CloudMusic\CloudMusic.exe"`、`.exe`、`a*b.exe` —— 前三次只产生 1 条 `cloudmusic.exe`（第 2、3 次提示「已在黑名单中」），后两次提示非法且配置不变；`config.json` 中该数组只有 `"cloudmusic.exe"`。
   **主干比较与等值匹配（正反两向都要验）**：① 拉黑 `msedge`（不带 `.exe`）与拉黑 `msedge.exe` 效果**完全相同**（主干等价）；② **反向验收**：拉黑 `music` **不会**误伤 `cloudmusic.exe` / `qqmusic.exe` / `music.ui.exe`（等值比较，**非子串匹配**）。
4. **按需枚举与零后台开销**：**只打开设置页（停在外观分区）不产生枚举**；首次点导航进入「黑名单」→「检测到的应用」列出当前在播应用（显示名 + 进程名）；点「加入」后该行消失并出现在黑名单列表、小组件 1s 内消失；点「刷新」可重新枚举且「上次检测」时间更新；「外观 ↔ 黑名单」来回切 5 次只枚举 1 次。**关闭设置页静置 5 分钟**：日志无任何枚举记录，60s `smtc 轮询统计` 调用量与 v1.7.1 基线一致（±10%），无新增 `[perf]` 慢记录。
5. **托盘置灰与即时性**：无任何媒体会话时打开托盘菜单，「拉黑当前应用」灰显不可点；有会话时可点，点击后小组件 ≤1s 消失，再开菜单显示「恢复当前应用（应用名）」且**可点**；点击后 ≤1s 恢复。

7. **双语与全拉黑**：语言切到 English，黑名单分区与托盘两项文案全英文、无中文残留、**无裸键名**、无截断、placeholder 也是英文；把测试机所有会产生会话的应用全部拉黑后，小组件永久不出现，程序不崩溃、CPU ≈ 0、日志无刷屏（黑名单命中日志被限流到 ≤1 条/进程名/60s）。
8. **W1 · 反查真的拿到了真实名**：找一个 `player_map` 静态表**外**的应用（Store 包 / UWP 最典型）开播 → 进入黑名单分区 → 该行 `process` **不是** AUMID 末段猜测值、且**没有**「进程名未能验证」小字；`config.json` 的 `media.app_names` 出现新的「AUMID → 进程名」条目。
9. **W2 · 缓存跨重启有效**：接着 W1 重启程序 → **不打开设置页**，直接播放该应用 → 日志里该会话的身份是**真实进程名**（说明判定走的是缓存的①级，没等枚举）；此时把该进程名**手输**进黑名单也**仍然命中**（缓存已落盘，不需要重新枚举）。
10. **W3 · 失败不静默（三档对照）**：① 手输 `zzz-test.exe`（本机从未出现过、不在静态表）→ 条目**照常入库** + toast「已加入。这个进程名还没在这台机器上出现过…」，**不报错、不回滚**；② 手输 `cloudmusic.exe` → **没有**这条提示；③ 从「检测到的应用」点「加入」→ 也没有这条提示（同源必命中）。
